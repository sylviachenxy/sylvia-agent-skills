# 首次设置与重新配置

目标是帮助用户完成并亲自验证一套工作链，而不是把配置格式交给用户自学。按未完成步骤继续；用户已明确的信息不重复询问。账号、路径、闹钟、关注对象与本机通过记录不能从另一用户继承。

开始先 `config list`，发现已有项再 `config show --profile ...`；没有时才新建，多个且未选默认时让用户选择。固定存储、命令及恢复细节见入口直接链接的配置持久化参考。不要让用户每次重报偏好，也不要仅从当前 context 恢复配置。

## 1. 决定内容和数据边界

先用自然语言问要看什么：天气、安排、待办、目标重点、指定关注动态，允许任意非空组合。确认每栏条数上限及哪些模块缺失时只能作为部分简报。first cut 按上述固定栏目顺序展示，仅输出启用项，不承诺可配置排序。关闭项无需权限、城市、来源测试或数据读取。

动态进一步确认对象/主题、纳入与排除规则、可靠来源偏好、语言。仅一个对象也有效；不要默认开启其他主题。天气启用才问城市。日历/列表启用后，先获准列举相应容器名称与 ID，再让用户精确选择，不先读正文。

Goal 启用才询问 Vault 根目录和允许读取的 Goal 主文件；路径解析后不得越界或经 symlink 指向别处。不要扫完整 Vault。首次只挑少数目标试跑。

说明原始信息可能交给 Codex 处理、正文会写进 iCloud Notes，锁屏通知默认不包含私人细节。确认独立私人 Notes 文件夹、profile ID、配置位置和本地私有 state_dir。账号/文件夹/profile 是一次绑定的稳定分发入口，不随日常偏好变动；以后换 iCloud 账号或入口需另做安装迁移。通常配置使用固定用户目录，state_dir 可选其中独立的私有运行状态子目录；自定义 profile 位置仍登记到固定 registry。folder/shared 属性不能仅靠名字判断；请用户在 Notes 确认不是共享文件夹或共享 Note。

## 2. 确定时间与运行环境

询问时区、信息回看窗口、日程前瞻窗口、预期起床时间及星期规律。展示绝对日期示例和实际跨度，确认 `0 < duration <= 24 小时`。例如昨晚 21:00→今早 06:00 为回看；今早 06:00→今晚 21:00 为前瞻。

回看结束后再最终采集，给生成及 iCloud 同步留出缓冲；用实测耗时调整，不承诺固定几秒可就绪。若想在 05:45 完成却回看到 06:00，先解决冲突。first cut 的一个 profile 保存一组钟点及适用星期，尚不支持同一入口的分星期多时段规则。用户需要工作日/周末不同钟点时，明确当前限制并先确定支持范围；不能用另建 profile、要求手机切换来冒充普通排程配置更新。

运行方式固定为起床前 Mac 生成。检查 Mac、Codex、网络及需要的本地应用在计划时段可运行；不能把云端任务当成本机 Vault/EventKit 的直接替代。不要自动改休眠或合盖设置。用户更改 iPhone 闹钟后，Mac 排程不保证自动跟随。

官方说明要求使用本地文件的定时任务运行时电脑开启、应用运行，且先手动测试再排程：[OpenAI Scheduled tasks](https://learn.chatgpt.com/docs/automations)。具体入口因当前客户端而异，使用当时实际可用的官方入口，不编造 CLI schedule 命令。

## 3. 建立配置并检查依赖

读取配置契约，以 `assets/config.example.json` 为格式示例，由 agent 填入刚确认的值，再展示用户可读摘要。示例是合成环境，不是现成可连接账号或真实订阅。不要把真实配置写回 assets。

先运行 `python3 scripts/morning-brief.py doctor`。它只检查工具存在，不读取应用或证明权限。Python 需要支持随附脚本；本 first cut 在 Python 3.11 验证。没有 Python 时先说明依赖，请用户选择安装方式，不偷偷安装。

启用 Calendar/Reminders 才检查 Swift 及只读 reader，按来源规则逐项请求系统权限；Notes 的 Apple Events 权限在首次显式验证时处理。不要索取 Full Disk Access、读取私有数据库或改用更宽权限路径。用户尚未授权时停止该步骤，而不是记成“无内容”。

先对草稿运行 `validate-config --config ...` 和适用日期的 `plan --config ...`，检查窗口、模块、主题、期限与状态目录。通过 `config save --expect-revision 0` 预览，用户确认后加 `--apply` 保存并登记；导入既有 JSON 保留其正 revision 与原 state_dir。是否设为默认须确认。保存后另起一次 CLI 调用 `config show --profile ...`，证明无需当前 context 也可找到并读回同一配置。

以后用 profile 调用 `checkpoint --stage config` 记录确认摘要，用 `setup-status` 看验收进度，用 `config status` 看手机/排程适配；这些不是同一状态。快照由工具管理，不直接修改 assets、registry 或版本文件。

## 4. 从离线样例到真实小范围试跑

1. 运行基础离线测试：`python3 -m unittest discover -s tests -p 'test_core.py'`、同样命令分别将文件名替换为 `test_cli.py`、`test_config_store.py`、`test_config_bindings.py`、`test_phone_protocol.py` 与 `test_notes_publisher.py`。只有启用 Calendar/Reminders 时再运行 `test_sources.py` 及 reader self-test；不要为仅动态/天气/Goal 的配置要求 Swift 或构建 reader。记录 `offline`；测试通过不等于原生权限通过。
2. 按白名单读取少量真实条目/目标，动态检索只限用户主题；逐项核对实际覆盖、日期语义和关联。确认禁用模块没有被读取。记录 `sources`，注明启用了哪些模块。
3. 先生成候选并 `render`，与用户核对内容和锁屏粒度。用真实“现在”及来源时间，不把仓库合成日期/网址冒充采集结果。
4. 确认本次 Notes 输出账号/文件夹后，使用受管 profile `publish --apply --setup-test` 试发，再 `verify`；记录 `local_publish`。该一次性试发允许手机/排程尚未适配，结果仍明确不是完整部署完成。不要新建/改用别的文件夹来绕过 target not found；结果不明按发布说明查证。

测试中创建的受管 Note 标明测试用途，保留到用户决定是否清理；不自动删除测试 Note、旧版或用户注释。

## 5. 在目标 iPhone 设置并验证

先运行 `config handoff --profile ...` 取得固定手机入口，依发布参考建立两条职责分离的快捷指令：通知检查、正文阅读。两条只绑定相同的 `protocol_version:2`、稳定 `config_id` 与 Notes 账号/文件夹；**不要填入配置 revision、时区、星期、生成/起床钟点或时间窗**。这些由每份正文动态提供，手机无需读取配置 JSON。可在 Mac 配置普通快捷指令后通过 iCloud 同步，但个人起床自动化要在该 iPhone 设置，不会因此自动同步过去。

先手动运行，确认它读取正确入口、正文完整校验通过、中文和链接正常、从 Safari 可以回到 Notes，再记录 `iphone_read`。首次验收还要用同一组不改动的手机参数读取两份不同配置版本的合成简报（含时间/时区变化），确认自动选择新版本并按正文绝对时间检查适用性；修改后的 fixture 必须由生成器重新校验/hash，不能在 Notes 手改标记求通过。随后创建一个可控测试闹钟或使用用户选择的起床触发，按系统实际支持设置立即运行；确认锁屏时通知先出现，点击时解锁不算后台执行失败。记录 `iphone_alarm`，再以当前配置指纹、实际设备/两快捷指令定位和观察证据执行 `config acknowledge --target iphone ... --apply`。没有用户报告或实测就不能登记已适配。

手机触发绑定“起床/停止闹钟”事件，不把 Mac 的 `wake_at` 复制成固定钟点自动化。在 Mac 修改预期起床时间只调整生成预算和必要的 Mac 排程，不改手机闹钟/触发器；它也不代表用户要求修改手机本身的闹钟。如果用户另行要求换闹钟或设备，作为明确设备操作处理，不混进普通偏好更新。

配戴 Apple Watch 时通知可能出现在手表；按目标使用方式验证，不能仅凭 iPhone 未弹出断言失败。不把一次锁屏成功推广为任何权限错误都能正常兜底。

手机校验逻辑变更后要回归对应分支。发现“仅日期检查”或 hash 提取未通过时，保留手动 Notes 阅读入口，明确自动就绪检查尚未完成，不能勾掉验证项。

## 6. 最后启用定时并交接

展示自动化的内容、时间、目标 profile 和本地运行前提，经用户确认后使用可用的 Codex 自动化工具/官方界面。默认遵循产品的当前任务内排程方式；只有用户要求独立任务时才选独立方式。不写私有 cron/launchd 来绕过产品能力，不给用户裸 RRULE。

使用 `config handoff` 给出的排程参数和提示，固定 registry 绝对位置和 profile ID，每次读取当前版本；不固定某个历史快照，也不跟随“默认 profile”。提示要求先通过 `config status --require-ready`，再按配置生成适用日、只读来源、向获准 Notes 目标发布，失败/冲突停止并报告，禁止改原生任务/Goal。不把 `--setup-test` 放入定时任务，不把整份偏好/正文/凭据复制进提示。

按官方自动化工具/界面保存后，读回核对实际时区、星期、执行时间、profile/registry 与发布范围，记录真实 automation ID，再执行 `config acknowledge --target automation ... --apply`。这证明记录了排程适配，不代替真正的定时运行。若存在旧任务，应精确更新而非再建一份；普通偏好更新也要检查是否改变了排程签名。手机通知和桌面失败报告分开，不声称两端状态已自动打通。

确认 `config status --require-ready` 通过后，执行一次真正的定时端到端测试，核对手机看到的版本与生成时间；记录 `timed_run`。再交接如何暂停 Mac 排程、停用手机个人自动化、手动重读、查看失败和调整偏好。

## 验证记录与后续修改

`checkpoint` 是 agent 根据实际观察或用户报告记录的证据，不是工具自动证明设备已就绪。证据须包含做了什么及结果，不抄私人正文。所有阶段有记录后仍检查证据是否属于当前设备、当前配置。

重新配置先读取当前 profile，基于原配置准备草稿并保留原 revision；用 `config save --expect-revision <当前版>` 预览、确认、应用，由工具递增。旧会话提交过期版本会失败，须重读合并，不硬改版本跳过。`config history/restore` 可恢复旧偏好为新版本。

保存后再次读回并检查 `config status`。普通偏好变更与恢复都保留手机入口的有效证据，**不更新快捷指令、不重新测试/acknowledge 手机**。内容或窗口变化而 Mac 排程未变时可继续生成；时区、星期或排程变化则只在 Mac 更新并验证实际自动化。恢复历史偏好也只按受影响的 Mac 参数复原，不自动复活旧外部排程。新偏好从下一次采集和新报告起使用；手机收到报告后自动读取，不能把“已保存”误报为“已同步”。

setup checkpoint 按配置指纹保留，不改写历史。`setup-status` 通过 `inherited_stages` 引用稳定手机绑定，明确表示沿用而非新做了设备测试；不能因为新指纹没有手机 checkpoint 就要求用户重做。其他不变范围可引用原证据，变更来源/排程只核查相应部分。日常改偏好不是首次 setup，不要求再逐项完成整套手机验收；也不得一键伪造全部阶段通过。

关闭模块立即影响后续采集和新输出，旧 Notes 历史不会自动删。增加账号/列表/Vault/主题来源，或提高正文与锁屏暴露范围，要重新确认。暂时读取失败只处理对应来源，不反复要求重做整套 setup。
