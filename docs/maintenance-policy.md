## 适用范围与维护责任

| --- | --- |
| 规范修订 | 2026-09-24，首次补齐生命周期与 SemVer；修订日期不是 plugin 版本 |
| 状态 | `approved`：维护者于 2026-09-24 确认，并授权通过 PR 合并到 main；不等于授权今后的破坏性操作 |

| 触发原因 | 用户要求在 marketplace 发布结构之外，补齐新建、编辑、归档、删除及 SemVer 规范 |
| 范围 | 所有可分发 skill、plugin、发现入口、兼容性、版本与退役记录 |
| 非范围 | 不更改教学标准、个人数据、许可证或其他仓库；不引入公司研发流程 |
| 复审时机 | 每次破坏性变更、重大宿主／安装器变化、进入 1.0 或发布事故后；普通局部编辑不重写规范 |

本文件规定“什么时候该怎么改”，[分发维护文档](plugin-development.md)规定目录、安装和验证操作。维护规范的批准不替代具体操作的授权；遇到影响用户数据、破坏兼容性或无法判定的情况先请求决策，不以规范擅自扩大权限。

## 1. 生命周期

这些状态是维护记录，不是新增的 SKILL frontmatter／plugin manifest 字段。不得写入宿主不支持的 `status` 字段，或以改名隐藏 `SKILL.md` 冒充下架。

| 状态 | 是否在当前默认分发中 | 维护含义 |
| --- | --- | --- |
| draft | 否 | 未验收设计只写在开发分支或普通设计文档中；不要把占位 skill 注册到已发布来源。 |
| active | 是 | 在声明范围内维护，入口、资源、测试和文档保持一致。 |
| deprecated | 是 | 仍可使用，已声明替代方式、迁移路径和拟退役版本；不是静默改变原功能。 |
| archived | 否 | 暂停维护并退出默认发现；保留最后可用版本、完整 Git SHA、旧路径和恢复依据。 |
| deleted | 否 | 明确移除，不再承诺恢复或支持；保留最小退役记录以免旧名称被误复用。普通删除不抹除 Git 历史。 |

通常为 `draft → active → deprecated → archived`；也可在明确授权后删除。归档／删除针对当前分发来源，不会自动卸载别人已经安装的副本、撤回历史 tag 或删除用户资料。

### 1.1 新建

1. 先确认真实使用场景、应触发／不应触发边界、输入输出、数据 Owner 与工具权限；与既有 skill 重叠时优先扩展现有职责，不创建同义入口。
2. 同领域 skill 加入现有 `plugins/<plugin>/skills/<skill>/`。只有确有新领域或独立安装价值才提议新 plugin；新 plugin 名称及分组由维护者确认。
3. 保持目录名、frontmatter `name` 和 UI 调用一致；资源完整自包含、不带占位文件或个人配置。只创建有实际用途的脚本、资料和测试。
4. 同步根／plugin README、明确列举技能的 starter prompts／接线、相关测试中的预期清单和 CHANGELOG；仅新增既有 plugin 内的 skill 时，不新增 marketplace 条目。
5. 验证显式调用、隐式触发、相邻非目标请求及失败／降级路径；脚本运行测试，分发变动按安装验收检查真实资源。通过后才纳入对外来源。
6. 给已发布 plugin 增加兼容能力通常升 minor；首次创建 plugin 默认从 `0.1.0` 开始，不因其所属仓库已有其他版本而照抄版本号。

### 1.2 编辑

1. 读当前 diff 和相关入口，保留用户改动；识别受影响的公开契约，再决定变更范围与版本级别。
2. 最小范围同步 `SKILL.md`、references、assets、scripts、`agents/openai.yaml`、接线和测试，避免入口与详细规则互相冲突。普通改字不要求重跑无关原生权限流程。
3. 持久状态、ID、CLI、JSON／回执、模板字段、评分证据含义有变化时，检查旧记录读取、迁移、恢复和消费者；不能用“只是 prompt／教材”跳过兼容性判断。
4. 新工具、强制依赖或更大数据访问范围需单独说明和授权；安装或修改技能不等于用户已同意读取账号／写入 Apple 数据。
5. 写明证据与未验证项；脚本失败、入口断链、资源缺失或兼容性未决时，不宣布完成对应交付。

### 1.3 弃用与归档

1. 普通退役 **Should** 先在至少一个对外版本中标记 deprecated，并说明替代方案（可为“暂无”）、迁移要求和最早移除版本。仅标记弃用也是版本变化，见 §2。
2. 归档前必须确认对象、理由、最后可用版本／SHA、受影响消费者和用户处理方式。用户只说“先别改它”不等于授权归档。
3. **skill 归档**：在移除活动目录前建立退役记录，再从所属 plugin 的 `skills/`、入口、默认提示和接线中撤出。所属 plugin 仍存在时，按移除公开能力计算版本；不能只把 README 条目删掉。
4. **整个 plugin 归档**：先安排弃用／迁移；退役时移除 marketplace 条目及活动 plugin 目录。记录最后发布版本和 catalog 撤出变更，不给已经不存在的 manifest 编造一个“退役版本”。如果移除的是 plugin 最后一个 skill，按整个 plugin 退役处理，不能留下空壳。
5. 归档源码以固定历史 Git SHA 保存；仓库当前树只留普通 Markdown 退役说明。**不要把完整旧包搬到 `archive/skills/` 或其他包含 `SKILL.md`／plugin manifest 的可扫描目录**，否则可能又被独立安装器发现。
6. 用干净快照确认退役对象不在新的默认 catalog／skills 发现集合，保留对象仍完整；更新校验器／测试中受影响的预期，而不是绕过失败。已安装旧副本可能继续存在，必须明确提示迁移，不声称已远程清除。

### 1.4 删除

- 删除需要明确对象和理由的授权；先列出依赖、资源所有权、最后可恢复 SHA、迁移／替代方案。普通清理不自动扩展成批量删除、清理用户机器或改写历史。
- 必需教材、词表、模板、脚本或公共资源被删除，也按公开能力／契约判断，不因为它们不是 `SKILL.md` 就按小修复处理。
- 更新所有入口、链接、消费者和测试，留下退役记录；正常删除优先经过弃用期，安全／隐私／权利风险可在明确确认后加急撤出，仍需记录影响与后续处理。
- 不删除 Obsidian 学情、Goal、用户偏好、账号绑定、提醒事项、日历、Notes 或其他个人产物。清理这些内容必须是另一个明确请求。
- Git 历史、既有 Release 和用户缓存可能仍保留内容；如需处理凭据泄露／历史清除，另行确定范围并授权，不通过强推、覆盖 tag 或删除普通文件声称“彻底清除”。退役说明不得再次暴露敏感内容。
- 曾发布的标识不得被赋给不相关的新功能。普通删除通常可从 Git 恢复；涉及风险撤回的版本不能再作为推荐恢复源。

### 1.5 重命名、跨 plugin 移动与恢复

- skill／plugin／marketplace 标识、安装选择器或所属 plugin 改变，视为迁移，不是纯目录整理。原安装方式不能继续工作时属于破坏性变更；有旧入口兼容桥接时也需验证两条路线，不能靠重复内容或软链接假装兼容。
- 跨 plugin 移动分别计算源包移除、目标包新增以及接线影响；两个 plugin 不强制升成相同版本。不能新增未经验证的自动依赖安装。
- archived 恢复时核对原因是否已消除、名称是否保留、资料／宿主是否仍有效，重新做行为和干净安装验收。还原的是代码，不是自动重放原生写入、定时任务或旧账号授权。
- 保持身份的恢复使用**高于该 plugin 历史已发布版本**的新版本（按本次兼容性判定），不回到 `0.1.0` 或重用旧 tag；旧历史不足以证明今日仍安全兼容。

### 1.6 退役记录

首次有实际退役对象时才创建 `docs/lifecycle/skill-<name>.md` 或 `docs/lifecycle/plugin-<name>.md`；现在不创建空记录。至少记录：

- `kind`、`name`、原 plugin／路径、`status`、生效日期、理由及批准依据（不写个人隐私或密钥）；
- 最后可用 plugin 版本、完整 Git commit SHA、旧路径；归档提供固定 SHA 的源码链接，风险删除说明该旧版不可推荐恢复；
- 替代项、受影响消费者、迁移步骤、用户数据处置边界、恢复条件；
- 撤出／恢复的 CHANGELOG 条目、变更所在提交和验证结果。尚未 commit 时明确写 pending，commit／push 后再核实补齐，不伪造未来 SHA。

记录不应包含可执行技能副本。不要删除旧记录以“重新使用”一个名称；状态变化追加历史。

## 2. SemVer

### 2.1 版本对象和公开契约

以 **plugin 为安装与 SemVer 单位**，唯一数值 authority 是 `plugins/<plugin>/.codex-plugin/plugin.json` 的 `version`。skill 随所属 plugin 版本交付，不另加重复 skill 版本；marketplace 按 Git SHA 追溯，不新增第二份 plugin version。

已有数据／协议／配置／题目或语料 schema version 各有职责，不能与 plugin 版本混为一谈或机械同时增加。CHANGELOG、tag、验收记录可以引用版本，但不能反过来覆盖 manifest。

本仓库的“公开契约”不只包括代码 API，还包括：

- 安装选择器、skill 名称／调用入口、声明的适用范围、职责和安全边界；
- 脚本 CLI、输入输出／回执结构、错误语义、模板字段、对其他 skill 的交接；
- 持久目录与文件命名、稳定 ID、配置／状态 schema、旧数据可读性；
- 已承诺的支持环境、强制依赖、用户授权、必需随包资料及其解释语义。

### 2.2 升版判定

依据 [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)；`0.x` 细分和纯文档 patch 是本仓库明确约定，不是声称上游强制所有项目如此执行。

| 本次对外变更 | 稳定期（≥1.0.0） | 当前开发期（0.y.z） | 典型例子 |
| --- | --- | --- | --- |
| 兼容修复／包内维护，无新公开能力 | patch：`1.2.3 → 1.2.4` | patch：`0.2.3 → 0.2.4` | 改错字、修链接、修实现 bug、补原本承诺的漏装资源；不改变数据或调用契约 |
| 向后兼容新增能力／声明弃用 | minor，patch 清零：`1.2.3 → 1.3.0` | minor，patch 清零：`0.2.3 → 0.3.0` | 新 skill、可选训练模式、旧配置仍有效的新选项；标记 deprecated 但仍保留能力 |
| 不兼容更改／移除能力 | major，minor／patch 清零：`1.2.3 → 2.0.0` | minor，patch 清零：`0.2.3 → 0.3.0`，**明确标注 BREAKING** | 改名、移出所属 plugin、归档／删除 skill、不兼容 CLI／状态格式、强制增加权限或最低环境 |
| 仅仓库级维护资料，不进入任何包 | 不升 plugin | 不升 plugin | 只改根 README、`docs/`、根 AGENTS 或维护工具；如实际改变安装契约仍按上面分级 |

- `0.x` 仍属未稳定契约，但不是隐藏破坏性变化的理由。不可把 breaking 放进 patch；发布记录必须区分“兼容新增”和“BREAKING”，即使两者都升 minor。
- `1.0.0` 表示愿意对明确公开契约提供稳定兼容承诺；由维护者确认范围、真实使用验证、升级／恢复路径后决定，不因日期、commit 数或测试条数自动升级。
- 多个变更合并发布时，每个 plugin 取最高影响等级；只给受影响的包升版。整 plugin 从 catalog 撤出按 §1.3 记录，不留下虚假的可安装空包。
- 正式版必须是无前导零的 `X.Y.Z`；manifest 不带 `v` 前缀。若创建版本 tag，采用 `<plugin>/vX.Y.Z`，指向包含该 manifest 和完整包的同一提交；tag／Release 仍需单独授权。

#### 常见灰区

- **提示词重写**：措辞精炼而约定不变可 patch；扩大职责或增加可选流程为 minor；取消原流程或改变原授权边界为 breaking，不按改动行数判断。
- **教材／考试标准更新**：勘误且契约不变可 patch；新增独立可选年份／标准为 minor；使历史评分、证据或配置含义改变时需明确版本标记、迁移及 breaking 判断，不能静默重算旧学情。
- **目录移动**：包内私有路径且已验证安装、公开命令、相对引用不受影响，才可能 patch；改变已公开路径、skill 所属 plugin 或默认内容集合属于 breaking。
- **只加测试／README**：位于 plugin 包内则至少 patch；只在仓库根维护目录、不改变分发行为则无需 plugin 升版。
- **新增依赖／权限**：真正可选、旧流程仍可使用可 minor；旧流程必须接受新权限／新工具／更高系统版本才能继续是 breaking，且版本号不代替授权。
- 无法证明兼容时写明疑点并请维护者裁决；不自行用低等级升版绕过迁移工作。

### 2.3 哪个时点必须升版

1. 与**上次对外分发的该 plugin 内容和 SHA**比较，不仅与上一个本地 commit 比较；同一轮未发布迭代可以累积变更，到交付边界统一判级。
2. 发布不只指 GitHub Release：将包变更推入用户可安装的 `main`／已对外提供的分发引用，也算对外分发。已有版本内容变化必须在该次 push 前升版并验证；不要“先推同版本，回头再 bump”。
3. 首次 `0.1.0` 尚未对外提供时可继续完善，不需要每次保存／本地 commit 都加版本。不能因为没有 tag 就认定以前已供安装的包“从未发布”。
4. 新版本号、包内容、文档、迁移说明和验证证据作为一个候选交付。没有 commit／push 授权时保留本地，不自动发布。

### 2.4 预发布、cachebuster 与不可变性

- 需要单独提供测试候选时用 `0.2.0-rc.1`、`0.2.0-rc.2` 等；稳定版号更高。预发布不代表自动通过正式验收，安装器如何选择版本须实际验证。
- `+codex.<标识>` 仅用于已获准的本地开发 cachebuster。SemVer 比较忽略 `+` 后的构建元数据，不能靠它声明新功能／breaking 或代替正式升版；开发缓存刷新按[现有操作流程](plugin-development.md)执行。
- 已对外提供的同一版本不能换内容，已发布 tag 不能移动、覆盖或复用。发现错误发布一个新版本；不手改安装缓存掩盖源文件／版本不一致。
- 回滚优先通过更高版本发布已验证的修复；如需用户临时固定到历史 SHA／版本，先确认安全性及新数据是否能被旧版读取。代码回滚不等于数据回滚，不自动逆向迁移或删档。

## 3. 规则与验收责任

`Must` 违反时阻塞受影响交付；`Should` 偏离需写出理由并由维护者确认。下表 Owner 的“维护者”均指仓库所有者或获授权 collaborator，agent 只执行获准范围。

| Rule ID | Level | Rule | Rationale | Applies To | Verification | Owner | Source |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SYL-LC-01 | Must | 按 §1.1 新建，单一实体内容源、同步发现入口 | 防重复／漏装 | 新 skill／plugin | 名称、资源、入口、安装与触发测试 | 维护者 | E1/E2/E3 |
| SYL-LC-02 | Must | 按 §1.2 评估契约后编辑，保护用户数据与授权 | 防静默改变行为 | 编辑／迁移 | diff、回归、旧状态和权限边界检查 | 维护者 | E2/E3 |
| SYL-LC-03 | Should | 正常退役前至少一个公开弃用版本 | 给用户迁移窗口 | 非紧急归档／删除 | 弃用记录、拟撤出版本、替代路径 | 维护者 | E3 |
| SYL-LC-04 | Must | 按 §1.3–1.6 退役／恢复，保留记录，不自动删用户安装和资料 | 防误卸载／不可追溯 | 归档／删除／恢复 | 授权、固定 SHA、发现集合、无悬空引用 | 维护者 | E2/E3 |
| SYL-VER-01 | Must | plugin 单一版本 authority，按 §2 的最高影响分级 | 让版本可解释 | 版本变更 | manifest、变更清单、兼容性说明 | 维护者 | E1/E4 |
| SYL-VER-02 | Must | 对外分发前升版，已发布版本不可变 | 防同版本缓存分裂 | main／分发引用／Release | 对比上次分发 SHA 和包内容、读回新版本 | 维护者 | E2/E4 |
| SYL-REL-01 | Must | 有迁移／恢复依据和验证证据才交付 breaking | 防用户被无提示中断 | 破坏性发布 | 旧数据 fixture、消费者、安装验证、维护者确认 | 维护者 | E2/E3 |

### 3.1 变更说明与验证矩阵

CHANGELOG 在未发布区按 plugin 记录：操作／状态、用户可见变化、旧版本 → 新版本（或首次版本）、分级依据、是否 BREAKING、迁移／替代方案、验证证据及未覆盖项。只改仓库规范应明确“不改变包版本”。归档记录不能只写“清理”。

| 变化 | 至少重审／验证的对象 |
| --- | --- |
| 普通包内文案／资料勘误 | 相关入口和引用、技能校验、被影响的行为；若资料有哈希封存，同步封存与测试 |
| 脚本／模板／状态协议 | 相关离线回归、旧配置／数据 fixture、错误与恢复路径、消费方 |
| skill／plugin 新增、移除、改名、归档、移动或恢复 | 根／plugin README、manifest／catalog、默认提示和接线、测试预期集合、干净安装＋运行时发现；退役对象不再默认发现 |
| version／安装器／发现布局 | 单一 authority、实际安装版本、完整资源和执行位、旧安装迁移说明 |
| 仅本仓库治理文档 | 链接、规则一致性、入口路由；不因文档改动声称原生设备 UAT 已重跑 |

命令见[分发验证层次](plugin-development.md#验证层次)。现有脚本自动验证的是结构、格式、内容完整性和发现；**bump 等级、退役授权、跨版本兼容性、tag 不可变性尚需人工／agent 基于证据审查**。新生命周期操作必须同步相应测试，不能声称现有 8-skill 快照已验证未来删除场景。

### 3.2 例外与下游重审

- 例外须记录申请人、对象、Rule ID、原因、风险、替代控制、批准人、有效版本／期限和复查条件，随对应变更说明保存；含私人信息的批准证据留在本地，公开记录只保留必要结论。到期未续批按默认规则处理。
- 例外不能绕过用户授权、隐私、许可证、凭据保护或谎报验证。紧急撤出可缩短弃用期，但不等于授权清除用户数据或 Git 历史。
- 安装器、公开契约、持久数据或分发结构变化时，先复查本规范及相关 README／接线／测试；不自动创建无关的 BRD、HLD 等文档。
- 本次需同步的是根 AGENTS、README、分发文档及 CHANGELOG。**规范获准采用不代表后续 breaking／归档／删除已获准；这些操作仍需在执行与发布前确认方案。** 维护者确认与独立 Guardrails Reviewer 准出是不同证据；未运行后者就不声称已通过。
